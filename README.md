# 复现前先查配置：用一个 Claude Skill 让 AI 把论文的实验设置逐项对到原文

> 要解决的阅读问题：要复现一篇论文，或者拿它当对比基线时，论文到底给了哪些实验设置、写在哪一页、哪些根本没写、哪些数字只适用于某个变体？
>
> 本文分享我的做法，并附上一次完整的真实实践：同一篇论文、同一个模型，加载 Skill 与不加载 Skill 各跑两次，按事先冻结的 32 项标准盲评。另外记录了一个失败案例，以及修复后的验证结果。

**结论先行**
- 两组公平对照中，加载 Skill 的一组得分都更高：59 vs 53、60 vs 52（满分 64）。盲评两次都判 Skill 组更好。
- 改善集中在三类最容易让复现跑偏的地方：
  - 分清变体口径，比如 select 和 revision；
  - 明确说出"论文没写什么"；
  - 交代成本口径。
- 代价：耗时约多 1.4 倍，客户端估算成本约多 1.5 倍。
- 它不能保证判断正确。在不完整的 PDF 上，第一版犯过一个系统性错误，见 §5。

## 1. 阅读难点出在哪

复现失败往往不是看不懂方法，而是漏了配置。这些配置在论文里散落在不同地方：

| 难点 | 本例中的样子（VeriHarness, arXiv:2610.00972v1） |
|---|---|
| 同一个"主结果"有多个变体 | 摘要里的 "6.2 / 6.4 points" 是**带 revision** 的结果 [p.1]，只做 select 的数字在表 2 另一行（51.6 / 53.7）[p.8]。第 1 页图 1 同样是带 revision 的结果 |
| 设置分散在正文、表注和附录里 | 模型和 thinking level 在 §4.1 [p.7]，基准子集与生成脚手架在附录 D [p.20]，判官模型在附录 D 的评分协议 [p.21]，成本口径在附录 K [p.27] |
| "唯一出现的数值"并不适用于主实验 | 全文只有一处 temperature，是附录 A 离线分析时"temperature zero" [p.19]，与验证器的解码设置无关 |
| 论文没写的东西最难发现 | 种子取值、显著性检验、验证器提示词全文、模型快照日期都没有给出；附录 I 还明说"do not establish statistical significance" [p.26] |
| 成本数字有估算和实测之分 | 多数投票、best-of-N、CLI 三行成本是"estimates … rather than metered runs" [p.27] |

方括号里的页码都可以在 [`paper/veriharness_excerpts.md`](paper/veriharness_excerpts.md) 对应的原文片段中核对。

直接让模型"读一下帮我理清复现配置"，在这个任务上有三种典型失败：只写主实验；把唯一出现的数值误当主设置；对"论文没写"的项目给不出明确判断。下文第 4 节的对照显示，即使是很强的模型也会在这三类上丢分。

## 2. 方法：把"查配置"拆成可检查的步骤

我把整个流程做成一个 Claude Code Skill（[`skill/SKILL.md`](skill/SKILL.md)）。核心设计有三点：

**(1) 固定清单，而不是开放式提问。** [`skill/references/checklist.md`](skill/references/checklist.md) 列了 26 个复现必需项，分 7 组：模型、数据、方法、评测、资源、产出、目标/风险。每项只能落在 6 种状态之一：`reported`（论文给出了可直接用的值）、`partial`（提到了但不够复现）、`not_reported`（查过，确实没有）、`conflicting`（前后不一致）、`not_applicable`、`not_in_material`（材料本身不完整，无法判断）。

为什么用清单：开放式提问时，模型会按"重要性"挑着写，长尾配置和"没写什么"最先被丢掉，而这些恰恰是复现时的坑。

**(2) 先逐页检索，再写"没报告"。** [`scan_config.py`](skill/scripts/scan_config.py) 为每个清单项准备了一组宽松的检索词，比如判官对应 `judge|verifier|grader|...`。脚本逐页统计命中，正文、附录分开列，自动跳过参考文献页。

规则是：某一项要标 `not_reported`，必须在 `searched` 字段里列出脚本给出的全部候选页，也就是先去看过才能说没有。这一步针对的是"把没看到当成没写"。

**(3) 门禁脚本：不过关就不能交付。** [`check_audit.py`](skill/scripts/check_audit.py) 检查核查表 `audit.jsonl` 的以下几点：
- 26 项是否全部覆盖，每种状态的必填字段是否齐全；
- 每条引文是否能在原文**逐字**找到、页码是否正确。脚本复用 [`verify_quotes.py`](skill/scripts/verify_quotes.py)，只容忍 PDF 提取带来的噪声，比如连字符断行、空格差异，改写过的引文过不了；
- `value` 字段里的每个数字是否都出现在对应引文中，防止"引文对、数字是编的"；
- 材料完整性（v1.1 加入）：正文提到、文件里却没有的表/图/附录，不能作为 `reported` 的依据；材料不完整时，报告正文不能写"论文未报告"。

检查不通过时，模型要按 PROBLEM 列表逐条修正后重跑。A1-with 的运行日志里就有这个循环：前两次检查分别查出 value 里有原文没有的数字，修正后才通过。

**为什么这样设计**：模型的弱点不是不会读，而是不知道自己漏了什么，也不会主动核对。清单解决"漏"，检索和 `searched` 字段解决"没看过就说没有"，门禁把"引文必须真实、数字必须出自引文"从提示词里的要求变成机器检查。这样做的取舍是更慢、更贵（见第 4 节）。

## 3. 真实案例：复现 VeriHarness 的 select 结果

- **论文**：Zhang et al., *VeriHarness: Scaling Agentic Verification for Long-Horizon Tasks*，arXiv:2610.00972v1，28 页，CC BY 4.0。
- **我的需求**（[`case_A/topic_card.md`](case_A/topic_card.md)）：我做 Agent 长程执行降幻觉方向，想把它当基线，先复现它的 select 结果。我只能调用闭源 API，单次复现预算约 200 美元。
- **给模型的提示**（[`case_A/prompt.txt`](case_A/prompt.txt)）：两组逐字相同，要求只依据论文本身，不联网。
- **事先冻结的验收标准**（[`case_A/acceptance.md`](case_A/acceptance.md)）：32 个必查要点（每项 2 分），6 个误读陷阱（每处扣 2 分），以及门槛。标准在任何运行之前写定。其中 51 处原文事实，我用脚本逐条对过原文。

### 实际输出（AI 输出，未经人工修改）

- 加载 Skill：[`runs/A1-with/report.md`](runs/A1-with/report.md)，核查表前若干行见 [`runs/A1-with/audit_first_rows.jsonl`](runs/A1-with/audit_first_rows.jsonl)，门禁结果见 [`runs/A1-with/check_report.json`](runs/A1-with/check_report.json)（66 行，26/26 项，problems = 0）。
- 不加载 Skill：[`runs/A1-without/report.md`](runs/A1-without/report.md)。

Skill 组报告的开头（原文摘录）：

> 复现就绪度：补齐 4 项后可以复现。复现 select 有一个很大的便利：作者公开了全部 rollout 池，每个 rollout 都附有基准判官的存档分数 [A2, p.22]……

## 4. 结果：公平对照与盲评

**对照条件**：两组都用 Claude Code 2.1.309、claude-opus-5-5（effort high），工具相同，预算上限都是 5 美元，都没有联网工具。每次运行都用全新的配置目录和工作目录。唯一差别是工作目录里有没有 `.claude/skills/repro-config-auditor/`，可在 [`runs/run_meta_*.json`](runs/) 的 `skills_visible` 核对。共两组独立配对，每组的两次运行同时启动。

**评分**：用一个新会话盲评，评分员只看冻结的标准、论文和两份报告。报告标为 X/Y，顺序由随机种子决定，种子和映射见 [`grades/blinding-*.json`](grades/)。评分员逐项打分，抽查带页码的说法，并列出原文中找不到的说法。完整评分在 [`grades/grade-A1.json`](grades/grade-A1.json)、[`grades/grade-A2.json`](grades/grade-A2.json)。

| 运行 | 总分/64 | 门槛 | 抽查与原文一致 | 原文找不到的说法 | 耗时 s | 估算成本 $ |
|---|---|---|---|---|---|---|
| A1 加载 Skill | **59** | 通过 | 12/12 | 0 | 747.8 | 2.16 |
| A1 不加载 | 53 | 未通过（没给就绪度结论） | 11/12 | 1 | 581.6 | 1.56 |
| A2 加载 Skill | **60** | 通过 | 12/12 | 0 | 988.0 | 2.75 |
| A2 不加载 | 52 | 通过 | 12/12 | 1 | 694.7 | 1.79 |

A2 两份报告的原文因篇幅限制没有放进本仓库；它们的逐项得分和评分理由都在 `grades/grade-A2.json` 里。

**差在哪里**（评分员的原话摘录，两组配对方向一致的才列）：

| 要点 | 加载 Skill | 不加载 |
|---|---|---|
| select 与 revision 的口径区分（G24） | 两次都得 2 分："明确 6.2/6.4 和 Figure 1 是含修订的数字，必须取 select 行" | 两次都得 1 分："没提醒摘要和首页的 6.2/6.4 是修订数字" |
| 种子取值与显著性未报告（G23） | 两次都得 2 分："附录 I 明说不确立统计显著性 (p.26)" | 两次都得 1 分："没有明确指出种子取值未报告" |
| 自进化实验的子集口径（G31） | 两次都得 2 分 | 1 分、0 分："完全没有覆盖自进化实验设置" |
| "论文没写什么"类 6 项合计 | 12/12、12/12 | 11/12、9/12 |

**不加载 Skill 反而更好的地方**也如实列出：
- 协议执行细节，"交付在裁决上下文中继续"（G14），两次都是不加载的一组更完整；
- 技能库的分类数量（G13）在 A1 中也是如此。

原因是清单里没有"协议执行顺序"这一独立项，这是这套方法的盲区。

"部分基线成本是估算、不是实测"（G27）这一项，A1 两组都漏了；A2 里只有加载 Skill 的一组写到了。所以它算不上稳定的改善。

**代价**：两对合计，耗时 1735.8 s vs 1276.3 s（+36%），客户端估算成本 $4.91 vs $3.35（+47%），对话轮数 23 vs 9–10。成本是 Claude Code 按标价算的客户端估算；我经第三方代理调用，实际计费拿不到。

**我的判断**：在"复现前查配置"这件事上，Skill 的价值不在于写得更多，而在于把三类最容易让复现跑偏的信息稳定地找全。只想粗看"能不能复现"时，多花的这 50% 未必值得。

## 5. 一个值得分享的发现：截断的 PDF 会让模型把"没看到"写成"没写"

我还专门做了一个异常测试：把同一篇论文只保留前 6 页（构造的截断 PDF，在 §4.1 第一句中途断开），用同样的提示要求核查复现配置，**不告诉模型文件被截断**。

**第一版（v1.0）两次都失败了**，评分记录见 [`failure_v1.0/grade-C2-v1.0.json`](failure_v1.0/grade-C2-v1.0.json)：
- 核查表里正确标了 `not_in_material`（材料缺失），但写报告正文时又滑回"论文未报告方差""主表用什么判官未报告"。可在完整论文里，这些都写在缺失的第 7 页之后。
- 摘要里写着"(Table 2)"的 6.2/6.4，在 Table 2 根本不在文件中的情况下，被标成了已核实的 `reported`。

**原因**：门禁当时只检查核查表，不检查报告正文；规则里也没写"所引表格不在材料中，就不能算核实"。模型在汇总时会回到训练中最常见的说法，也就是"论文未报告"。

**改进（v1.1）**：
1. `check_audit.py` 自动检测正文提到、文件里却没有的表/图/附录。检测方法是比对 "Table 2" 这类引用和 "Table 2 |" 这类表题，附录比对标题行。
2. 依赖这些缺失对象的 `reported` 行直接报错。
3. 材料不完整时，报告正文里出现"未报告"而同一句没有说明材料缺失，也报错。

**验证**：
- 新门禁在 v1.0 的两份失败输出上准确报出了上述问题（[`failure_v1.0/check_v1.1_on_v1.0_C2.json`](failure_v1.0/check_v1.1_on_v1.0_C2.json) 列出了检测到的缺失对象：Table 2/5、Appendix A/B/C/F/H）。
- 在完整论文的输出上没有误报。
- 用 v1.1 重跑截断案例两次，必须项全部通过：两次 `not_reported` 都是 0，6.2/6.4 都标为"Table 2 缺失，未能核实"。
- 本文第 4 节的 A 组对照用的也是 v1.1。

**适用条件**：这个检测依赖"表题/附录标题能在提取文本中找到"。如果某篇论文的表题被 PDF 提取打散，可能误报缺失；这时需要人工确认。

## 6. 复现步骤

1. 安装：`npm install --prefix tools/cc @anthropic-ai/claude-code@2.1.309`；`python3 -m venv venv && venv/bin/pip install pymupdf==1.26.5`，并把 `venv/bin` 放到 PATH 前面。
2. 把 `skill/` 复制为 `<工作目录>/.claude/skills/repro-config-auditor/`。
3. 在工作目录放入论文 PDF（arXiv:2610.00972v1）和你的课题卡，然后发出与 [`case_A/prompt.txt`](case_A/prompt.txt) 相同的请求。Skill 会按描述自动触发，也可以输入 `/repro-config-auditor`。
4. 检查结果：
   - `output/check_report.json` 中 `problems` 为空；
   - 报告中的 select 目标数字应为 Flash 51.6 / Opus 53.7 [p.8]，而不是摘要里的 6.2 / 6.4；
   - "论文未报告"至少应包括种子取值、显著性、验证器提示词全文。

   全部 32 个要点见 [`case_A/acceptance.md`](case_A/acceptance.md)，可以逐条对照。
5. 想复跑对照：用 [`tools/run_case.py`](tools/run_case.py) 为每次运行新建配置目录和工作目录，再用 [`tools/blind_grade.py`](tools/blind_grade.py) 盲评。API 凭据在运行时从本机的 `~/.claude/settings.json` 读取，不在仓库内。

我自己按这些步骤，在一个全新目录里复跑过一次加载 Skill 的运行，盲评 58/64，与上表一致。复跑记录不在本仓库内，只在比赛的作品包里。

- 论文：VeriHarness（arXiv:2610.00972v1），CC BY 4.0。本仓库只收录核查所需的原文片段（`paper/`），完整版请到 arXiv 下载。
- 代码：`skill/`、`tools/` 下的全部脚本、清单、模板、验收标准和课题卡，都是本次由我（借助 Claude Code）编写的。其中只有 PyMuPDF/pypdf 是第三方库。
- AI 输出：`runs/` 下的报告和核查表是模型的原始输出，未经人工修改；`grades/` 是盲评会话的原始输出。
- 我的判断：第 1、4、5 节中"我的判断""原因""适用条件"等段落，以及对评分结果的归纳。
- 局限：
  - 只有一篇论文、两组配对；
  - 盲评与被评是同一个模型，可能有同源偏好；
  - 标准由我一人写定；

  - 没有使用玻尔科学空间。
