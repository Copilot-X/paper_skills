# 复现前先查配置：让 AI 把论文的实验设置逐项对到原文

> `repro-config-auditor`：一个 Claude Code Skill。要复现一篇论文、或拿它当对比基线之前，先把"论文给了哪些设置、在第几页、哪些没写、哪些数字只属于某个变体"查清楚。
>
> 模型：claude-opus-5-5（effort high）｜ 宿主：Claude Code 2.1.309 ｜ 论文：VeriHarness（arXiv:2610.00972v1，CC BY 4.0）
>
> 一条命令核对本文所有数字：`python3 tools/verify_article.py`（只用 Python 标准库，检查全部通过）

---

## 0. 五分钟速览

**我要解决的阅读问题。** 复现论文失败，很少是因为看不懂方法，多半是漏了配置。比如：

- 判官模型写在附录的评分协议里；
- 摘要里的提升数字其实属于另一个变体；
- 唯一出现的 temperature 只在离线分析里用过；
- 种子和显著性检验根本没写。

这些往往要等结果对不上了才回头去找。

**我的做法。** 把"查复现配置"拆成三步，每一步都能检查：

1. 固定 26 项清单，每项只能落在 6 种状态里；
2. 写"论文没写"之前，必须先逐页检索候选页；
3. 门禁脚本强制检查：引文必须能在原文逐字找到，数值必须出自引文。

**实际效果。** 同一篇论文、同一个模型，加载 Skill 与不加载 Skill 各跑两次，按事先冻结的 32 项标准盲评：

| | 第 1 组 | 第 2 组 |
|---|---|---|
| 盲评总分（满分 64）：加载 / 不加载 | **59 / 53** | **60 / 52** |
| 盲评员判谁更好 | 加载 Skill | 加载 Skill |
| 门槛（必须给出复现就绪度结论等） | 通过 / **未通过** | 通过 / 通过 |
| "论文没写什么"6 项小计（满分 12） | 12 / 11 | 12 / 9 |
| 耗时（秒） | 747.8 / 581.6 | 988.0 / 694.7 |
| 估算成本（美元） | 2.16 / 1.56 | 2.75 / 1.79 |

两组方向一致：Skill 稳定地多找到了三类最容易让复现跑偏的信息（§4.1）。代价是两组合计耗时 +36%、估算成本 +47%（§4.4）。不加载 Skill 在"协议执行细节"上两次都更好，这是方法的盲区（§4.3）。

**在玻尔科学空间里真实跑了一次。** 我把同一份提示词交给玻尔的 scimaster 智能体，带 Skill 和不带 Skill 各跑一次（Photon 支付，未动现金），同样用冻结标准盲评：**54 / 51**（满分 64）。差距比本地小，"论文没写什么"6 项仍是 **12 / 8**。过程中踩到的坑（沙箱没有 PyMuPDF、读文件工具会脱敏输出、计费命令要显式确认等）和经验见 §6。

## 0.5 阅读约定：三种陈述分开标记

| 标记 | 含义 | 去哪核对 |
|---|---|---|
| **【原文】** | 论文的逐字内容 | [`paper/veriharness_excerpts.md`](paper/veriharness_excerpts.md)，按页码查找 |
| **【AI】** | 模型的原始输出，未经我改写 | [`runs/`](runs/)（门禁结果与运行记录）、[`grades/`](grades/)（盲评会话的输出）、[`bohrium/scimaster_run/`](bohrium/scimaster_run/)（玻尔里两次运行的完整报告） |
| **【判断】** | 我基于前两者的推理或归纳，论文本身没有这么说 | 正文中标注；涉及数字的，都能用 `tools/verify_article.py` 复算 |

这三类的边界在产物层面也由机器检查，不只靠措辞：核查表里 `reported` 状态的行必须带逐字引文和页码，`value` 里的每个数字必须出现在引文中，门禁脚本会强制检查（§2.3）。

## 1. 问题：为什么"查复现配置"比"读懂方法"更难

### 1.1 难在五件事同时存在

以本次实践的论文为例。表中都是【原文】，页码可在 `paper/veriharness_excerpts.md` 核对：

| 难点 | 本例中的样子 |
|---|---|
| 同一个"主结果"有多个变体 | 摘要写 "6.4 points with Claude Opus 4.8" [p.1]，这是**带 revision** 的结果。只做 select 的数字在表 2 另一行：Flash 51.6、Opus 53.7 [p.8] |
| 设置分散在正文、表注和附录里 | 模型和 "thinking level high" 在 §4.1 [p.7]；基准子集在附录 D [p.20]；判官模型在附录 D 的评分协议 [p.21]；成本口径在附录 K [p.27] |
| 唯一出现的数值不是主实验设置 | 全文只有一处 "temperature zero"，出现在附录 A 的离线分析里 [p.19] |
| 论文没写的最难发现 | 种子取值、显著性检验、验证器提示词全文、模型快照日期都没给出。附录 I 甚至明说 "do not establish statistical significance" [p.26] |
| 成本有估算也有实测 | 多数投票、best-of-N、CLI 三行成本是 "estimates … rather than metered runs" [p.27] |

### 1.2 为什么换个更好的提示词解决不了

【判断】三类失败都和"模型不知道自己漏了什么"有关：

- 开放式提问时，模型按重要性挑着写，长尾配置最先被丢掉；
- 模型很少主动说"这一项论文没写，我查过第 x 页"；
- 汇总时，模型会回到训练中最常见的说法。

提示词只能"要求"它做到，没法"检查"它是否做到。第 4 节的不加载组用的就是一份写得很清楚的提示词，仍然在这三类上丢分。

### 1.3 我给自己定的边界

- 只做"读论文、查配置"，不运行论文代码，也不判断方法好坏；
- 只依据论文本身，不联网（代码仓库只作为"查找建议"）；
- 不读图里的数值（图里的数字标为"需人工读图"）。

## 2. 方法：拆成可以检查的步骤

完整流程见 [`skill/SKILL.md`](skill/SKILL.md)。下面讲三个关键设计，以及为什么这样设计。

### 2.1 固定清单 + 6 种状态（[`skill/references/checklist.md`](skill/references/checklist.md)）

26 项复现必需配置，分成 7 组：模型、数据、方法、评测、资源、产出、目标/风险。每项只能取下面 6 种状态之一：

| 状态 | 含义 | 必填字段 |
|---|---|---|
| `reported` | 论文给出了可直接用的值 | 逐字引文、页码、值 |
| `partial` | 提到了但不足以复现（"见代码""沿用前人"） | 引文、页码、缺什么 |
| `not_reported` | 查过，确实没有 | 查过的页、缺什么、去哪补 |
| `conflicting` | 前后不一致 | 两处引文和页码 |
| `not_applicable` | 本文不涉及 | 原因 |
| `not_in_material` | 材料本身不完整，无法判断 | 查过的页、去哪补 |

**为什么这样设计**：把"论文没写"和"材料里看不到"拆成两种状态，是从一次失败里学到的（§4.2）。多值项（多个模型、多个基准）必须拆行写，防止只写主实验。

### 2.2 先逐页检索，再说"没写"（[`scan_config.py`](skill/scripts/scan_config.py)）

脚本为每个清单项准备一组宽松的检索词，例如判官对应 `judge|verifier|grader|...`。然后逐页统计命中次数：正文、附录分开列，跳过参考文献页。要把某一项标为 `not_reported`，必须在 `searched` 字段里列出脚本给出的全部候选页，门禁会检查这一点。

**为什么**：这一步专门对付"把没看到当成没写"。检索词宁宽勿窄，因为漏掉一页的代价，比多看一页大得多。

### 2.3 门禁脚本，不通过就不能交付（[`check_audit.py`](skill/scripts/check_audit.py)）

| 检查 | 防的是什么 |
|---|---|
| 26 项全覆盖，每种状态的必填字段齐全 | 漏项 |
| 引文能在原文**逐字**找到、页码正确（复用 [`verify_quotes.py`](skill/scripts/verify_quotes.py)，只容忍 PDF 提取噪声，比如连字符断行、空格） | 改写或编造的引文 |
| `value` 里的每个数字都出现在引文中 | "引文是真的，数字是编的" |
| 写 `not_reported` 时列出了全部候选页 | 没看过就说没有 |
| 材料完整性：正文提到、文件中却没有的表/图/附录，不能支撑 `reported`；材料不完整时，报告正文不得出现"论文未报告" | 把"文件缺页"当成"论文没写"（v1.1 新增，见 §4.2） |

检查不通过时，模型要按 PROBLEM 列表逐条修正后重跑。A1 加载 Skill 那次运行中，前两次检查都查出 value 里有原文没有的数字，修正后才通过。这一点在运行日志里可以看到，这里只记录结论。

## 3. 案例：复现 VeriHarness 的 select 结果

### 3.1 输入与读者条件

- **论文**：Zhang et al., *VeriHarness: Scaling Agentic Verification for Long-Horizon Tasks*，arXiv:2610.00972v1，28 页（正文 1–12、参考文献 12–17、附录 18–28），CC BY 4.0。
- **读者条件**（[`case_A/topic_card.md`](case_A/topic_card.md)）：Agent 长程执行降幻觉方向；只能调用闭源 API；单次复现预算约 200 美元。卡片里"过去两次复现返工"是情景设定，没有可核验记录。
- **提示词**（[`case_A/prompt.txt`](case_A/prompt.txt)）：两组逐字相同，要求只依据论文本身。
- **事先冻结的验收标准**（[`case_A/acceptance.md`](case_A/acceptance.md)）：32 个必查要点（每项 2 分，其中 6 项是"未报告"类），6 个误读陷阱（每处扣 2 分），以及门槛。标准在任何运行之前写定。其中 51 处原文事实，我用脚本逐条对过。

### 3.2 结论与理由（【AI】，加载 Skill 那组的原文摘录）

> 复现就绪度：补齐 4 项后可以复现。复现 select 有一个很大的便利：作者公开了全部 rollout 池，每个 rollout 都附有基准判官的存档分数 [A2, p.22]……

本地运行的核查表共 66 行、26/26 项，门禁结果 [`check_report.json`](runs/A1-with/check_report.json) 中 problems = 0。**本地 A1 两份报告的全文因材料容量限制没有收录**（只留门禁结果、运行记录和盲评记录），所以上面这段摘录无法在包内逐字核对。可逐字核对的完整报告是玻尔里那一组：带 Skill 见 [`bohrium/scimaster_run/with_skill/report.md`](bohrium/scimaster_run/with_skill/report.md)，不带见 [`without_skill/report.md`](bohrium/scimaster_run/without_skill/report.md)，对比见 §6。

### 3.3 公平对照怎么做的

- 两组的宿主、模型、effort、工具白名单、权限、预算上限（5 美元）都相同，也都没有联网工具。
- 每次运行都用全新的配置目录和工作目录，没有记忆，没有 CLAUDE.md。
- **唯一差别**是工作目录里有没有 `.claude/skills/repro-config-auditor/`。可以在 [`runs/run_meta_*.json`](runs/) 的 `skills_visible` 核对，脚本也检查了这一点。
- 共两组独立配对，每组的两次运行同时启动。

### 3.4 我核查了什么、怎么核查的

- **盲评**：用一个新会话，只给它冻结的标准、论文和两份报告。报告标为 X/Y，顺序由随机种子决定，种子和映射见 [`grades/blinding-*.json`](grades/)。评分员逐项打分，抽查带页码的说法（每份 12 条），并列出原文中找不到的说法。完整记录见 [`grades/grade-A1.json`](grades/grade-A1.json) 和 [`grades/grade-A2.json`](grades/grade-A2.json)。
- **抽查结果**：加载 Skill 两次都是 12/12 与原文一致，原文找不到的说法为 0；不加载 Skill 是 11/12 和 12/12，各有 1 处与原文不一致的说法。例如 A1 不加载组写"CLI 差值正好卡在 2.0"，而表 2 里 JobBench 那一格实际差 2.1。
- **复算**：本文所有数字都能用 [`tools/verify_article.py`](tools/verify_article.py) 从包内文件重新算一遍（§5.3）。

## 4. 实践发现

每个发现都按同一结构写：**现象 → 证据 → 改进 → 验证 → 在什么条件下有效、什么条件下失效**。

### 4.1 Skill 稳定改善的是"口径"和"没写什么"，而不是"写得更多"

- **现象**：两组的总分都是加载 Skill 更高（59 vs 53、60 vs 52）。但差距不在篇幅，A1 两份报告的长度相近。
- **证据**：两组方向一致的条目，下表数字为【AI】盲评员打的分。

| 要点 | 加载 Skill（A1 · A2） | 不加载（A1 · A2） | 盲评员的理由摘录 |
|---|---|---|---|
| G24 区分 select 与 revision 口径 | 2 · 2 | 1 · 1 | 不加载组"没提醒摘要和首页的 6.2/6.4 是修订数字" |
| G23 种子取值、显著性未报告 | 2 · 2 | 1 · 1 | 加载组指出"附录 I 明说不确立统计显著性 (p.26)" |
| G31 自进化实验的子集口径 | 2 · 2 | 1 · 0 | 不加载组 A2"完全没有覆盖自进化实验设置" |
| "未报告"类 6 项小计 | 12 · 12 | 11 · 9 | — |

- **改进对应**：G24 对应清单项 T1（主结果要写明变体）以及"多值项拆行"；G23 对应 E3/E4 加上"写 not_reported 前要先查过候选页"；G31 对应 D2（实际使用的子集）。
- **何时有效**：论文有多个变体、附录信息多、有"没写"的配置时。本例的附录占 11 页，正属于这种情况。
- **何时失效**：如果论文很短、配置全在一张表里，清单的边际价值会小很多。这一点我**没有验证**，只有一篇论文。

### 4.2 截断的 PDF 会让模型把"没看到"写成"没写"（一次失败与修复）

- **现象**：我把同一篇论文只保留前 6 页（构造的截断 PDF，在 §4.1 第一句中途断开），提示词不提截断。第一版（v1.0）两次运行都没过必须项。
- **证据**：[`failure_v1.0/grade-C2-v1.0.json`](failure_v1.0/grade-C2-v1.0.json)，E3、E4 都是 0 分。
  - 核查表里正确标了 `not_in_material`，报告正文却写成"论文未报告方差""主表用什么判官未报告"。这些在完整论文里都有，只是写在缺失的第 7 页之后。
  - 摘要里标着"(Table 2)"的 6.2/6.4，在 Table 2 不在文件中的情况下，仍被标为已核实的 `reported`。
- **原因**【判断】：门禁当时只检查核查表，不检查报告正文；规则也没写"所引表格不在材料中，就不能算核实"。
- **改进（v1.1）**：
  1. `check_audit.py` 自动列出正文提到、文件里却没有的表/图/附录。方法是比对 "Table 2" 这类引用和 "Table 2 |" 这类表题，附录比对标题行。
  2. 依赖这些缺失对象的 `reported` 行直接报错。
  3. 材料不完整时，报告正文出现"未报告"、而同一句没说明材料缺失，也报错。
- **验证**：
  - 新门禁在 v1.0 的失败输出上报出 9 个问题，列出了 7 个缺失对象（[`failure_v1.0/check_v1.1_on_v1.0_C2.json`](failure_v1.0/check_v1.1_on_v1.0_C2.json)）；在完整论文的输出上没有误报。
  - 用 v1.1 重跑截断案例两次，必须项全部通过。这两次重跑的原始输出不在本仓库内，在比赛的作品包里。
  - 第 4 节的 A 组对照用的就是 v1.1。
- **何时失效**：检测依赖"表题和附录标题能在提取文本中找到"。如果 PDF 提取把表题打散了，可能误报缺失，需要人工确认。

### 4.3 盲区：清单没覆盖的东西，Skill 反而做得更差

- **现象**："交付在裁决上下文中继续"这类协议执行细节（G14），两组都是不加载 Skill 的一组更完整（1 vs 2、1 vs 2）。A1 的技能库分类数量（G13）也是这样（1 vs 2）。
- **原因**【判断】：模型严格按 26 项清单组织输出，清单里没有"协议执行顺序"这一独立项。不加载 Skill 的一组自由写作，反而顺带写到了。
- **改进方向（未实施，因此不声称已验证）**：在清单的 P1（方法流程）里加入"各阶段的上下文与交接方式"。

### 4.4 代价：更慢、更贵

- **证据**：两组合计，耗时 1735.8 s vs 1276.3 s（+36%），客户端估算成本 $4.91 vs $3.35（+47%），对话轮数 23 vs 9–10。数据见 `runs/run_meta_*.json`，脚本已复算。
- **原因**：门禁循环（检查、修正、再检查）加上逐项填表。
- **何时不值得**：只想粗看"能不能复现"时。成本是 Claude Code 按标价算的客户端估算；我经第三方代理调用，实际计费拿不到。

## 5. 复现：怎么自己跑一遍

### 5.1 环境与预算

| 项 | 值 |
|---|---|
| 宿主 / 模型 | Claude Code 2.1.309 / claude-opus-5-5，effort high。经第三方代理接入，精确快照版本**无法取得** |
| 依赖 | Python 3.10 以上；PyMuPDF 1.26.5（`extract_text.py` 需要，没有时退回 pypdf）。其余脚本只用标准库 |
| 预算 | 单次运行上限 5 美元，实际估算 1.56–2.75 美元 |
| 人工参与 | 只有运行**之外**的事：写课题卡、任务和标准，冻结哈希，启动运行，核对评分。没有人工修改任何输出 |

### 5.2 操作步骤

1. 安装：`npm install --prefix tools/cc @anthropic-ai/claude-code@2.1.309`；`python3 -m venv venv && venv/bin/pip install pymupdf==1.26.5`，并把 `venv/bin` 放到 PATH 前面。
2. 把 `skill/` 复制为 `<工作目录>/.claude/skills/repro-config-auditor/`。
3. 在工作目录放入论文 PDF（arXiv:2610.00972v1）和课题卡，发出 [`case_A/prompt.txt`](case_A/prompt.txt) 里的请求。Skill 会按描述自动触发，也可以输入 `/repro-config-auditor`。
4. 想复跑对照：用 [`tools/run_case.py`](tools/run_case.py) 为每次运行新建配置目录和工作目录，再用 [`tools/blind_grade.py`](tools/blind_grade.py) 盲评。API 凭据在运行时从本机读取，不在仓库内。

### 5.3 怎么判断结果是否符合预期

| 检查 | 通过标准 |
|---|---|
| 门禁 | `output/check_report.json` 中 `problems` 为空，26/26 项覆盖 |
| 复现目标是否取对 | select 目标数字是 Flash 51.6 / Opus 53.7 [p.8]，**不是**摘要里的 6.2 / 6.4 |
| "没写什么"是否说全 | 至少包括种子取值、显著性检验、验证器提示词全文、模型快照日期 |
| 不误读 | 不把附录 A 的 temperature zero 当成主实验设置；不把估算成本当成实测成本 |
| 全部 32 个要点 | 对照 [`case_A/acceptance.md`](case_A/acceptance.md) 逐条打分 |
| 本文数字 | `python3 tools/verify_article.py` 输出 ALL PASS |

`verify_article.py` 还包含**反向用例**：它构造一份含伪造引文、错误页码、编造数字的核查表，确认门禁三处都会报错，并且不会误伤真实引文。

我自己按这些步骤，在一个全新目录里复跑过一次加载 Skill 的运行，盲评 58/64，与上表一致。复跑记录在比赛作品包里，不在本仓库。

## 6. 玻尔科学空间：真实运行一次，以及踩到的坑和经验

我用玻尔官方命令行工具 `bohr`（2.9.5）做了两件事：一是把同一份论文 PDF 交给 Uni-Parser 解析并与 PyMuPDF 对比（§6.1）；二是在玻尔的 scimaster 智能体里**把同一个任务真实跑两遍**，带 Skill 和不带 Skill（§6.2）。全部用 Photon 支付，没有动现金。

### 6.1 PDF 解析：Uni-Parser 与 PyMuPDF 的对比

- **做法**：`bohr pdf parse --file veriharness_2610.00972v1.pdf --table 2 --textual 1 --sync --payment-source photon`，再用 `bohr pdf result <token>` 取结果（免费）。28 页解析成功，计费 1.40 元，用 Photon 支付。摘录见 [`bohrium/uniparser_table2_excerpt.json`](bohrium/uniparser_table2_excerpt.json)。

| | PyMuPDF（本 Skill 默认） | 玻尔 Uni-Parser |
|---|---|---|
| 表 2 | 一格一行，要靠表头顺序自己对列 | 直接还原成 Markdown 表格行，表头和 6 列对齐 |
| 正文关键设置 | 我抽查的 13 项全部能找到 | 同样 13 项全部能找到 |
| 标题与页眉 | 正确 | 小型大写标题识别成 "VERiHARNEs s" |

- **经验**：要从表格里取"变体 × 基准"的数字时，Uni-Parser 更省事；但它的输出带 LaTeX 包裹（`\(53.3 \pm 1.2\)`）、标题有 OCR 误差，不能直接用于逐字引文校验。门禁改用它的输出需要先去掉 LaTeX 标记，我没有实现。

### 6.2 在智能体里真实运行本 Skill

盲评是用一个全新的 Claude Code 会话完成的（脚本 `tools/rca_grade_bohrium.py` 与 §3 的盲评同源，只改了读取哪两份报告，X/Y 随机，映射见 [`blinding.json`](bohrium/scimaster_run/blinding.json)，评分见 [`grade_blind.json`](bohrium/scimaster_run/grade_blind.json)，省略了抽查明细）。

**我对云端那份"带 Skill"的结果做的核对**（不只信模型自报）：

1. 云端自报门禁 `problems = 0`。我把它产出的 `paper.txt`、`audit.jsonl` 取回本地，用同一个 `check_audit.py` 重跑：退出码 0，81 行、26/26 项、problems = 0（[`check_report_local_recheck.json`](bohrium/scimaster_run/with_skill/check_report_local_recheck.json)）。

**盲评发现的问题**（如实写出）：

- 差距（+3）比本地两组（+6、+8）小。只有一次运行，不能据此说"在玻尔里效果更好或更差"。

### 6.3 在玻尔里踩到的坑和经验

下面每条都来自这次真实运行的记录（命令输出或智能体的运行流），不是事后推测。

| # | 现象 | 原因或证据 | 怎么处理 |
|---|---|---|---|
| 1 | 登录后命令仍报未登录 | `bohr auth status` 显示 `refresh_required`，设备码 5 分钟过期，换过一次的码不能复用 | 无头环境用两步设备码：`bohr auth login --device --no-wait --json` 拿码，用户授权后 `bohr auth login --resume` |
| 2 | `bohr agents run` 什么都没跑就退出 | 返回 `CONFIRMATION_REQUIRED`（"nothing ran and nothing was charged"） | 计费命令在非交互环境要显式 `--yes`；同时加 `--payment-source photon`，避免余额不足时回落到现金 |
| 3 | 新建会话上传文件返回 503 | 上次不带 `--agent` 时 `Failed to ensure session` | 上传时带 `--agent <id> --session new`，一步完成建会话和上传 |
| 4 | 沙箱里没有 PyMuPDF，Skill 的提取脚本报缺依赖 | 运行流里智能体先试 `pip install pymupdf`（装了一半），再装 `pypdf`，`extract_text.py` 走回退路径 | Skill 的回退设计起了作用，报告里也声明了。但云端与本地提取器不同，页码一致、文字略有差异，所以门禁要用**云端那份 paper.txt** 复核 |
| 5 | 智能体读文件时看到 `[REDACTED_EMAIL_ADDRESS]`、`[REDACTED_PHONE_NUMBER]` | 运行流里它发现 Read 工具会对输出做隐私脱敏，而 `grep` 看到的原始文件是正常的 | 需要核对数字或引文时用 grep 或脚本，不要只信 Read 的显示。这与昨天 Uni-Parser 里表 2 末位变占位符是同一类现象 |
| 6 | 云端报告里 `Algorithm 1` 被门禁列为"材料中缺失" | pypdf 提取丢了算法框；`check_report` 里 `material_missing_objects = ["Algorithm 1"]` | 这是提取差异，不是论文缺失；门禁的材料完整性检测在这里确实起作用 |
| 7 | 只登记了 1 个交付物（report.md） | `bohr agents artifacts list` 只列出登记过的交付物，审计表等在工作区里 | 用 `bohr agents artifacts download --session <id> --path <相对路径> --out <本地>` 逐个取回 |
| 8 | 中断本地进程后云端任务仍在跑 | 我杀掉本地进程后，云端任务仍然跑完并产出了报告（昨晚那次的 25,950 字节报告就是这样得到的） | 不要假设杀掉本地进程就停止了云端任务；到会话里用 `artifacts list` 取回结果 |
| 9 | 想知道这次运行花了多少 Photon，算不出 | `bohr billing photon` 的账本里没有智能体运行的明细；账号下同时有别的任务在扣费，余额差不等于这次的成本 | 我**不声称**具体数字。只能说：现金余额全程没变（−2.64 元），支付走 Photon |

**如果你也想在玻尔里跑 Skill**，我的建议顺序：先用一个极短的提示词探测智能体能否看到上传的文件（我第一次探测时它说没检测到文件，原因是当时上传 503 了）；再上传 Skill 压缩包和论文；提示词里明确要求"先读 SKILL.md、每一步用自带脚本、告诉我门禁退出码"；运行结束后**不要只看智能体的回答**，把 `audit.jsonl` 和 `paper.txt` 取回本地重跑门禁。

**局限**：每个条件只有一次运行；对照组不是预先设计的；盲评员与被评运行同属一个模型家族；Photon 成本无法给出。因此这一节证明的是"Skill 能在玻尔智能体里被完整执行，产出能通过独立复核"，不是"玻尔里效果更好"。

## 7. 适用边界

- **适用**：有实验的单篇实证、方法或基准论文，文字层可提取；要复现论文或拿它当基线时。
- **不适用**：判断方法好不好；跨多篇综述；纯理论证明；读取图中的数值；运行论文代码。
- **没验证过的**：只用一篇论文做了对照；在玻尔里每个条件只跑了一次；盲评员和被评运行是同一个模型，可能有同源偏好；验收标准由我一人写定。
- **刻意的取舍**：它宁可写"未报告，已查 p.x–p.y"，也不给出看起来完整的配置表。这会让报告不那么"漂亮"，但复现时最需要的正是这部分。
